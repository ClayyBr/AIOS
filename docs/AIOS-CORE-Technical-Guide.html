1. Visão Geral e Propósito

O Synkra AIOS (AI-Orchestrated System) é um framework de desenvolvimento auto-modificável alimentado por IA. Fundado em Desenvolvimento Ágil Dirigido por Agentes, oferece capacidades revolucionárias para desenvolvimento dirigido por IA e transformação de qualquer domínio com expertise especializada.

O AIOS organiza agentes de IA para trabalharem como uma equipe real: cada agente possui papel, responsabilidades e regras definidas. Em vez de interagir com uma IA genérica, o AIOS garante:

  • Cada agente sabe exatamente o que fazer (persona, capabilities, dependencies)
  • Agentes se comunicam entre si passando documentos e contexto
  • Existe um processo claro do início ao fim (Planning → Development → QA → Deploy)
  • A qualidade é verificada automaticamente por gates multi-camada
Natural Language First: Todo o framework é escrito em linguagem natural (Markdown/YAML). Não há código de programação no core — apenas instruções em linguagem natural que agentes de IA interpretam e executam.

O AIOS é domain-agnostic: funciona para desenvolvimento de software, entretenimento, escrita criativa, estratégia de negócios, educação, gestão financeira de restaurantes, e qualquer domínio que possa ser representado por agentes especializados.

2. Premissa Arquitetural: CLI First

O Synkra AIOS segue uma hierarquia inegociável de prioridades que deve guiar TODAS as decisões:

Camada Prioridade Foco Exemplos
CLI Máxima Onde a inteligência vive. Toda execução, decisões e automação. Agentes (@dev, @qa), workflows, comandos
Observability Secundária Observar e monitorar o que acontece no CLI em tempo real. Dashboard SSE, logs, métricas, timeline
UI Terciária Gestão pontual e visualizações quando necessário. Kanban, settings, story management

Princípios Derivados

  1. A CLI é a fonte da verdade — dashboards apenas observam, nunca controlam
  2. Funcionalidades novas devem funcionar 100% via CLI antes de ter qualquer UI
  3. A UI nunca deve ser requisito para operação do sistema
  4. Observabilidade serve para entender o que o CLI está fazendo, não para controlá-lo
  5. Ao decidir onde implementar algo, sempre prefira CLI > Observability > UI

3. As Duas Inovações-Chave

🧠 1. Planejamento Agêntico

Agentes dedicados (@analyst, @pm, @architect) colaboram com você para criar documentos de PRD e Arquitetura detalhados e consistentes. Através de engenharia avançada de prompts e refinamento com human-in-the-loop, estes agentes produzem especificações abrangentes que vão muito além da geração genérica.

⚙️ 2. Desenvolvimento Contextualizado

O agente @sm (Scrum Master) transforma planos detalhados em stories hiper-detalhadas que contêm tudo que o @dev precisa: contexto completo, detalhes de implementação e orientação arquitetural incorporada diretamente nos arquivos de stories.

Problema resolvido: Esta abordagem de duas fases elimina tanto a inconsistência de planejamento quanto a perda de contexto — os dois maiores problemas no desenvolvimento assistido por IA. O agente dev abre uma story com compreensão completa do que construir, como construir e por quê.

4. Constitution & Governança

O AIOS possui uma Constituição formal (v1.0.0) com princípios inegociáveis e gates automáticos que bloqueiam violações:

Artigo Princípio Severidade Descrição
I CLI First NON-NEGOTIABLE Toda funcionalidade nova funciona 100% via CLI antes de UI. Dashboards observam, nunca controlam.
II Agent Authority NON-NEGOTIABLE Cada agente tem autoridades exclusivas. Apenas @devops pode git push, criar PRs e releases.
III Story-Driven MUST Nenhum código é escrito sem story associada. Stories têm acceptance criteria claros.
IV No Invention MUST Specs não inventam — derivam de requisitos funcionais, não-funcionais, constraints ou research.
V Quality First MUST Lint, typecheck, tests e build devem passar. CodeRabbit sem issues CRITICAL.
VI Absolute Imports SHOULD Sempre usar imports absolutos com alias @/. Relativos criam acoplamento.

Gate Severity Levels

Severidade Comportamento Uso
BLOCK Impede execução, requer correção NON-NEGOTIABLE, MUST críticos
WARN Permite continuar com alerta MUST não-críticos
INFO Apenas reporta SHOULD

5.4 Template Processing System

O AIOS emprega um sofisticado sistema de processamento de templates orquestrado por três componentes:

  • template-format.md — Define a linguagem de markup: {{placeholders}} para substituição de variáveis, [[LLM: instructions]] para diretivas AI-only, blocos condicionais
  • create-doc.md — Engine de orquestração que gerencia geração de documentos, interação com usuário, validação
  • advanced-elicitation.md — Camada de refinamento interativo com 10 ações de brainstorming estruturado

6.4 Princípios de Design de Agentes

  • Dev Agents devem ser Lean — Mínimo de dependências, foco em código. Cada linha conta.
  • Web/Planning Agents podem ser maiores — Tasks e templates mais complexos são aceitáveis.
  • Agentes definem roles, Tasks são procedures, Templates são outputs.
  • Dependencies explícitas — Cada agente declara exatamente o que precisa.
  • Startup Instructions — Agentes carregam documentação do projeto automaticamente ao ativar.

7. Story-Driven Development

No AIOS, nenhum código é escrito sem uma story. Este é um princípio MUST da Constitution.

Anatomia de uma Story

  • O que precisa ser feito (acceptance criteria detalhados)
  • Por que precisa ser feito (contexto de negócio, valor para o usuário)
  • Como implementar (orientação técnica, referências arquiteturais)
  • Checklist para acompanhar progresso ([ ] → [x])
  • File List com todos os arquivos modificados

Workflow Completo

@po cria story com acceptance criteria
    → @sm enriquece com contexto técnico hiper-detalhado
        → @dev implementa marcando checkboxes
            → @qa testa e valida (review 10 fases)
                → @devops faz push seguro
                    → Ciclo reinicia com próxima story
Key Insight: Stories são o mecanismo de transferência de contexto entre agentes. Quando o @sm cria uma story, ele embute toda a orientação arquitetural, decisões do @architect, e requisitos do @pm. O @dev recebe um arquivo auto-suficiente.

10. ADE — Autonomous Development Engine

O motor de desenvolvimento autônomo transforma requisitos em código funcional através de 7 Epics:

Epic Nome Descrição Técnica
1 Worktree Manager Isolamento de branches via Git worktrees. Cada feature em ambiente isolado com auto-create on story start e auto-cleanup.
2 Migration V2→V3 Migração para formato autoClaude V3. Inventory assets, analyze paths, migrate agents em batch.
3 Spec Pipeline Transforma requisitos em specs executáveis. Gather requirements → assess complexity → research deps → write spec → critique spec.
4 Execution Engine Executa specs com 13 steps + self-critique. Create plan → create context → execute subtasks sequencialmente.
5 Recovery System Recuperação automática de falhas. Track attempts, rollback, retry com ajustes baseados no erro.
6 QA Evolution Review estruturado em 10 fases. Review build → request fix → verify fix → approve/reject.
7 Memory Layer Memória persistente de padrões e insights. Capture insights, list gotchas, apply learned patterns.
User Request → Spec Pipeline → Execution Engine → QA Review → Working Code
                                        ↓ (falha)
                               Recovery System
                                        ↓
                                Memory Layer

11. Quality Gates — 3 Camadas de Validação

⚡ Camada 1: Pre-commit (Local)

Performance: <5s com cache habilitado

  • ESLint — qualidade de código
  • TypeScript — verificação de tipos
  • Validação de filenames

📋 Camada 2: Pre-push (Local)

Validação de stories e consistência

  • Checkboxes de stories completas
  • Consistência de status
  • Seções obrigatórias presentes

☁️ Camada 3: CI/CD (Cloud — Obrigatório para merge)

  • Todos os testes automatizados
  • Cobertura de testes mínimo 80%
  • CodeRabbit automated review (self-healing: auto-fix para CRITICAL e HIGH)
  • GitHub Actions workflows completos
  • Build de produção com sucesso

Comandos de Validação

npm run lint              # ESLint
npm run typecheck         # TypeScript
npm test                  # Jest
npm run test:coverage     # Cobertura
node .aios-core/utils/aios-validator.js pre-commit   # Gate 1
node .aios-core/utils/aios-validator.js pre-push     # Gate 2
node .aios-core/utils/aios-validator.js stories      # Validar stories

13. MCP & Infraestrutura

O AIOS integra nativamente com o Model Context Protocol (MCP) via Docker:

Servidor MCP Função API Key
context7 Documentação atualizada de bibliotecas para LLMs Não
desktop-commander File management, terminal commands, system operations Não
playwright Browser automation para testes e web interaction Não
exa AI-powered web search e content extraction Sim (EXA_API_KEY)

Presets

  • Minimal (default): context7 + desktop-commander + playwright — sem API keys, ~10-15k tokens
  • Full: Todos + exa — requer EXA_API_KEY, ~20-25k tokens

Gateway Docker

docker compose -f .docker/mcp/gateway-service.yml up -d  # Start
curl http://localhost:8080/health                          # Health check
docker mcp server ls                                       # List servers

14. IDE Sync & Integrações
